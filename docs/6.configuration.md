## Module option

| Key | Type | Default | Description |
| --- | --- | --- | --- |
| `backendUrl` | `string` | `http://localhost:5010` | The origin the sidecar calls the DMS backend on, for its pages registry and logs. Set it to `${@api.API_LOCAL_BASE_URL}`. |

The module ignores an empty or non-string `backendUrl`, and the sidecar then uses the default. The [Settings](/docs/modules/assistant/usage/settings) page holds every other setting.

The `builder.api.enabled` key mounts the database connect routes. [Database connection](/docs/modules/assistant/database-connection#configuration) describes it.

## Environment variables

| Variable | Read by | Effect |
| --- | --- | --- |
| `DMS_ASSISTANT=0` | Backend | The backend starts without the sidecar. |
| `NODE_ENV=production` | Backend and sidecar | The backend starts no sidecar, and a sidecar started by hand exits. |
| `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN` | Sidecar | A Claude credential. It wins over every other Claude login, and the onboarding window cannot change it. |
| `CLAUDE_CONFIG_DIR` | Sidecar | The folder of the Claude Code CLI's login, in place of `~/.claude` and `~/.claude.json`. |
| `OPENAI_API_KEY` | Sidecar | Ignored. Codex runs on a ChatGPT sign-in, and the sidecar logs a warning once per start when the variable is set. |
| `DMS_ASSISTANT_CODEX_ALLOW_VERSION_MISMATCH=1` | Sidecar | Runs a `codex` binary outside the supported range, and logs the mismatch. |
| `XDG_CONFIG_HOME`, `APPDATA` | Sidecar | The base folder of the saved Claude token and the ChatGPT sign-in. See [Sign in with your plan](#sign-in-with-your-plan). |

The sidecar passes the backend's environment to Claude Code.

## Agent providers

The assistant runs on Claude Code, the default, or on Codex. **Coding agent** on the Settings page picks the provider. Both providers behave the same in the chat, with tool calls, approval requests and file-change animations.

A provider that cannot run fails the turn and shows the reason in the chat. Its package may be missing, or its sign-in gone. The assistant never hands the conversation to the other provider: you may have picked one provider precisely so that your code does not reach the other.

Switching the provider ends the live sessions of the previous one. An open conversation loses the agent's memory and keeps its transcript.

### Enable `codex`

Codex needs the `codex` CLI at a supported version and a ChatGPT sign-in.

The `codex` CLI is an optional peer dependency, so installing the module never installs it. Its platform binary takes several hundred megabytes. The sidecar runs the versions that `peerDependencies["@openai/codex"]` accepts in the module's `package.json`, from the version its protocol types come from up to the latest 0.x release:

```bash [Terminal]
pnpm add @openai/codex@<supported version>
```

The sidecar reads `codex --version` once per start and refuses a version outside that range. The chat then names both versions and the one to install. Restart the backend after you install the CLI, then pick **Codex** under **Coding agent** on the Settings page.

### Sign in with your plan

Codex runs on your ChatGPT plan through [Sign in with ChatGPT](https://developers.openai.com/siwc), with no OpenAI API key. You sign in from the [onboarding window](/docs/modules/assistant/onboarding#sign-in-with-chatgpt-for-codex) or with **Sign in with ChatGPT** on the Settings page. Both open OpenAI's consent page. After you allow access, OpenAI sends the browser back to `http://127.0.0.1:<sidecar port>/auth/chatgpt/callback`.

- On the machine that runs the DMS, that address is the sidecar, and the sign-in completes in that tab.
- On a DMS that runs elsewhere, such as a cloud development server, that address points at your own computer and does not load. Copy the whole address from the address bar and paste it in the window, or under **Paste the return address** on the Settings page. The code in the address works once, within 10 minutes, and only for the sign-in attempt that produced it.

The sign-in belongs to the user and the machine, so every DMS project on that machine shares it. The sidecar stores it in `chatgpt-auth.json`, with file mode `0600`, never in the project. A Claude token saved from the onboarding window goes to `claude-auth.json` in the same folder:

| Platform | Folder |
| --- | --- |
| Windows | `%APPDATA%\dms-assistant` |
| Other, with `XDG_CONFIG_HOME` set | `$XDG_CONFIG_HOME/dms-assistant` |
| Other | `~/.config/dms-assistant` |

An access token lasts an hour, and the sidecar refreshes it before it expires. The refresh token lasts 30 days and changes on each refresh. Codex usage counts toward your plan's limits, which you can cap per app in ChatGPT's settings. When a limit is reached, turns fail with OpenAI's message, and nothing switches to paid API usage.

**Sign out** on the Settings page revokes the session. Codex then stops in every DMS project on the machine until you sign in again. To remove the `dms-assistant` app from your ChatGPT account, disconnect it in ChatGPT's settings.

## Where the chat's tools come from

Every chat session, on Claude Code and on Codex, gets two MCP servers:

| Server | Tools | How the session reaches it |
| --- | --- | --- |
| `dms` | The builder, database, mockup, `typecheck`, `query_logs`, `list_pages` and `page_verify` tools of `@antelopejs/dms` | `node <project root>/node_modules/.cache/dms/mcp-bridge.cjs`, the launcher the DMS writes in development |
| `dms-assistant` | `ask_user`, `get_current_page`, `find_pages_using` and `navigate_to_page`, which drive the dashboard tab or the chat | The sidecar |

The agent sees the tools as `mcp__dms__builder_add_block`, `mcp__dms-assistant__ask_user` and so on. The `dms` server also serves a `navigate_to_page`. The chat hides it, so the agent sees one tool of that name.

`navigate_to_page` waits for the page's data blocks to settle and lists the charts, KPIs, lists and tables that rendered empty or failed. A page that looks done but shows no data is therefore not reported as done. An `@antelopejs/dms` without block states gives the plain navigation result.

The database tools, `database_connections`, `database_relations`, `database_describe` and `database_profile`, read the catalog and the aggregates of a connected database, never its rows.

The DMS writes the launcher only when its MCP server is on, which by default means in development. Set `mcp.backendUrl` in the `dms` module's config to `${@api.API_LOCAL_BASE_URL}`, as [MCP server](/docs/ai-and-claude-code/mcp-server#configuration) in the DMS docs shows. Without the launcher, the chat has no builder tools, and Safe mode can change nothing.

The chat runs the tools of both servers without asking, in every approval mode, except in two cases:

- The `dms` server holds a deletion, a project configuration change, a mapping that would remove pages, `builder_remove_query` and `builder_remove_field`. It refuses the first call and says what the call would do. The agent then asks you with `ask_user`, and only the same call repeated within 10 minutes runs.
- While **Always ask for** covers block removals, `builder_remove_block` and `builder_move_block` ask on a card first.

Any other MCP tool asks on Claude Code. Codex refuses it.

A Claude Code or Codex session you start yourself in the project gets the same `dms` server from the project's `.mcp.json`, with no assistant installed. [MCP server](/docs/ai-and-claude-code/mcp-server) in the DMS docs covers it. Outside the chat, the approval modes, Safe mode, Activity and Changes do not apply.

## How Safe mode blocks edits

In Safe mode, the agent changes the project only through the builder tools of the `dms` MCP server, whatever the approval mode.

- On Claude Code, a `PreToolUse` hook lets through only reads, web access, sub-agents, the MCP tools the chat runs without asking, and tools that change nothing outside the chat. `Read`, `Glob` and `Grep` run without asking inside the workspace and ask outside it. The hook refuses every other tool: file edits, shell commands, scheduled tasks, tools that act outside the chat, and any tool it does not know, such as one a Claude Code update adds.
- On Codex, the sandbox stays read-only and without network, and the sidecar declines every escalation.

A switch between Safe mode and Code mode applies from the next tool call on Claude Code, and from the next turn on Codex. The conversation stays.

## Secret files

The project's database URLs and other credentials live in `.env`. The agent can read none of the `.env` and `.env.*` files, in every approval mode and in both scopes. `.env.example`, `.env.sample` and `.env.template` stay readable.

- With Codex, the sandbox refuses to read these files anywhere in the project and its local modules. Codex checks again before each command, so it also covers a secret file created during the chat, and a command you approve to run outside the sandbox. The sidecar declines, without asking, a Codex patch that writes one of these files or renames a file onto one, through a symbolic link too, whatever rule you kept.
- With Claude Code, the hook refuses a read or an edit that names one of these files, or a symbolic link to one, even before the file exists.

## What the chat renders

The chat treats nothing the agent writes as markup:

- Markdown renders with raw HTML off, then an allowlist sanitizes it.
- Links go only to `http`, `https` or `mailto` addresses or to a page of the dashboard, and they open in a new tab.
- An image the model writes shows as a link.
- The agent can send the dashboard only to pages of the dashboard's own origin.

## Remote access

The sidecar listens only on `127.0.0.1`. The browser reaches it through the DMS frontend server, so the assistant works wherever the dashboard does, and the sidecar's port and credential stay on the server.

| Route | Use |
| --- | --- |
| `GET /ai/channel/events` | Event stream from the sidecar |
| `POST /ai/channel/:connectionId/messages` | Messages from the browser |

The module declares `/ai/**` as a backend proxy of the frontend server (`backendProxies`), with the session of the signed-in member. The views, the blocks and the chat call the module's routes on the dashboard's own origin, and the frontend server forwards them to the backend. The DMS frontend must support `backendProxies`.

::note
Browsers keep at most six HTTP/1.1 connections per origin, and each dashboard tab already holds two. The assistant adds one in a visible tab while its panel is open, while a chat in it works or waits for you, or while the command palette streams an answer. Over HTTPS with HTTP/2, the limit does not apply.
::
