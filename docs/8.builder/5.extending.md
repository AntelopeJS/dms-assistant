The builder has no editor of its own. Its clients, such as the [AI assistant](/docs/modules/assistant/introduction), the DMS dashboard or your own tooling, drive its operations through the interface or the HTTP API.

## The interface

[`@antelopejs/interface-dms-builder`](https://github.com/AntelopeJS/dms-builder/tree/main/packages/interface-dms-builder/docs) exposes every operation as an `InterfaceFunction`. A module in the same process imports an operation and calls it like any async function.

```ts [src/seed-page.ts]
import { AddBlock } from "@antelopejs/interface-dms-builder";

export async function seedRevenuePage(): Promise<void> {
  const result = await AddBlock({
    page: "/revenue",
    name: "total",
    type: "KpiCard",
    config: { title: "Total revenue", icon: "i-ph-currency-eur" },
  });
  if (result.ok) {
    console.log(result.data.path); // "/revenue#total"
  }
}
```

A mutation returns an `OpResult`. On success it is `{ ok: true, data, changes }`, where `changes` lists the files the operation changed, with optional `warnings`. On failure it is `{ ok: false, error }`. The interface reference covers these topics:

## The HTTP API

Every route sits under `/api/builder` and requires an authenticated tenant owner. A route that runs a mutation, or a read that can fail, answers with the interface's `OpResult`, so a client branches on `ok` rather than on the status code. The list reads (`GET /catalog`, `GET /pages`, `GET /categories`, `GET /resources`, `/query-templates` and `/data-sources`) and the reads that describe the project (`/status`, `/tables/usage`, `/page/impact`, `/page/access` and `/permissions`) answer with their value. `/page/impact` and `/page/access` answer `404` with `{ code: "not_found", ref }` for an unknown page.

| Method | Path | Body or query | Operation |
| --- | --- | --- | --- |
| `GET` | `/status` | | `{ ok: true, projectRoot }`, the project root the builder edits |
| `GET` | `/catalog` | | `GetCatalog` |
| `GET`, `POST` | `/pages` | `CreatePageInput` | `ListPages`, `CreatePage` |
| `GET`, `POST` | `/categories` | `CreateCategoryInput` | `ListCategories`, `CreateCategory` |
| `PUT`, `DELETE` | `/category` | `{ category, patch }`, `?ref=` | `ConfigureCategory`, `DeleteCategory` |
| `GET`, `DELETE` | `/page` | `?ref=` | `GetPageStructure`, `DeletePage` |
| `POST` | `/page/configure` | `{ page, patch, expectedVersion? }` | `ConfigurePage` |
| `POST` | `/page/preview` | `{ page, draft }` | `PreviewLayout` |
| `POST` | `/page/blocks` | `{ page, draft, expectedVersion? }` | `SetPageBlocks` |
| `GET` | `/page/impact` | `?ref=` | What deleting the page takes with it |
| `GET` | `/page/access` | `?ref=&permission=` | Who reaches the page and each of its blocks |
| `GET` | `/permissions` | | The permissions the DMS registered |
| `GET`, `POST` | `/resources` | `CreateResourceInput` | `ListResources`, `CreateResource` |
| `GET` | `/resource` | `?ref=` | `GetResourceStructure` |
| `POST` | `/resource/configure` | `{ resource, patch, expectedVersion? }` | `ConfigureResource`, the routes a table serves |
| `POST`, `PUT`, `DELETE` | `/resource/fields` | `{ resource, field, expectedVersion? }`, `{ path, patch, expectedVersion? }`, `?path=` | `AddField`, `ConfigureField`, `RemoveField` |
| `GET` | `/tables/usage` | | `{ readers, rows }`, the pages reading each table and its rows in the request's tenant |
| `GET` | `/query-templates` | | `ListQueryTemplates` |
| `GET` | `/data-sources` | `?responseKind=` | `ListDataSources` |
| `POST`, `PUT`, `DELETE` | `/queries` | `{ page, input, expectedVersion? }`, `{ query, patch, expectedVersion? }`, `?ref=` | `AddQuery`, `ConfigureQuery`, `RemoveQuery` |
| `POST` | `/query-preview` | `{ query, args? }` | `PreviewQuery` |
| `GET` | `/query-preview` | `?query=<JSON>` and the route's own parameters | The answer the saved query's route would serve |
| `POST` | `/refresh` | | `RefreshSourceIndex`, then `{ ok: true }` |

In a `/page/configure` or `/category` patch, an option sent as `null` is removed from the file.

Both query previews read the tenant from the request, never from the body. `GET /query-preview` answers with the bare body the route will serve once saved. If it cannot run the query, it answers `400` for a malformed request, `404` for `not_found` and `422` for any other error.

### Database routes

These routes serve the flow that connects an existing database, which starts from **Start from an existing database** in the assistant's onboarding popup. Rows of an external database reach the owner through `/database/sample` only. No interface function of the builder returns them.

| Method | Path | Body or query | Answer |
| --- | --- | --- | --- |
| `GET` | `/database/connections` | | Each catalog connection, with `id` and what its provider reports (`engine`, `version`, `database`, `role`) or an `error` |
| `POST` | `/database/connections/repair` | `{ dryRun? }` | An `OpResult` of the configuration change, or an empty success when nothing is missing. See [Repair a connection made before](#repair-a-connection-made-before). |
| `POST` | `/database/connections/check` | `{ engine, url }` | `{ reachable, latencyMs?, user?, canRead, canWrite, reason? }`. Owner only, and `403` outside development. `400` for an `engine` other than `postgres`, `mongodb` or `rethinkdb`, or a `url` that is not of that engine. See [Check a connection before writing it](#check-a-connection-before-writing-it). |
| `POST` | `/database/analyse` | `AnalyseDatabaseInput` | `AnalyseDatabase` |
| `GET` | `/database/analysis` | `?id=` or `?connection=` | `GetAnalysis`, or the latest analysis of the connection. `404` when the connection has none. |
| `POST` | `/database/map` | `MapResourcesInput` | `MapResources` |
| `GET` | `/database/mapping` | `?connection=&module=` | `GetMapping` |
| `GET` | `/database/project` | | `{ modules, self, ownDatabase?, databasePins, dmsDatabase? }`. See [What connecting a database writes](#what-connecting-a-database-writes). |
| `POST` | `/database/project` | `{ steps, opts?, variables? }` | `ConfigureProject`. With `variables`, the builder first writes their development values into `.env`. |
| `GET` | `/database/connection` | `?connection=` | `{ wiring, details }`. `404` for an unknown connection. |
| `POST` | `/database/connection/remove` | `{ connection, dryRun? }` | An `OpResult` of the configuration change |
| `POST` | `/database/connection/url` | `{ connection, url }` | An `OpResult` with the `variable` it set. A URL without a password keeps the current one. |
| `POST` | `/database/sample` | `{ connection, relation, columns, limit }` | The sampled rows. `404` for an unknown connection. |

A route that refuses the request answers `422` with `{ code: "refused", message }`.

#### What connecting a database writes

The **Connect a database** form plans one `ConfigureProject` batch from the answer of `GET /database/project`, and sends it to `POST /database/project`. The answer names `self`, the id `antelope.config.ts` gives this module, `ownDatabase`, the project's default `interface-database` provider, `databasePins`, the modules to pin to it, and `dmsDatabase`, the id of the `dms-database` entry. `ownDatabase` and `dmsDatabase` are absent when the project has no such database or module. The route refuses with `422` when the configuration does not say plainly which database is the default, when a module that imports `interface-database` and does not provide it is not written as an object literal, a version string or an entry with a spread or a member under a computed name, so the builder cannot write its pin, or when `dms-database` is only written that way under its id or its package name. An entry with a spread that already pins `interface-database` in an `importOverrides` written after its last spread or computed name counts as pinned, since a later key wins. A module keyed by a computed name, a method or an accessor may be `dms-database` or a module that needs a pin, so it is refused too.

The batch writes these steps in order:

1. `AddModule` for the engine's driver, with its URL read from a variable.
2. `CreateLocalModule` for the module that holds the tables, pinned to the driver.
3. `ConfigureModule` on `self`, declaring the catalog connection under the connection's id.
4. `ConfigureModule` on `dms-database`, when the project has it and an own database. The entry then reads, for a connection `erp` served by the driver `builder-db-erp` over a project whose own database is `mongodb`:

   ```ts
   const modules = {
     "dms-database": {
       importOverrides: [
         { interface: "@antelopejs/interface-database", source: "mongodb" },
         { interface: "@antelopejs/interface-database", source: "builder-db-erp", id: "erp" },
         { interface: "@antelopejs/interface-database-catalog", source: "builder-db-erp", id: "erp" },
       ],
       config: { externalConnections: { erp: { access: "read" } } },
     },
   };
   ```

   The first entry of `interface-database` without an id is the binding a plain import reaches, so the own database comes first. The connection keeps one id on both interfaces and in `externalConnections`. `access` is `read`, or `read-write` when the form chose it, and `read` when absent.
5. One `ConfigureModule` for each module in `databasePins`. Once a second `interface-database` provider exists, core refuses to start a module that imports `interface-database` without a pin, so each configured module that imports it, does not provide it and has no pin without an id gets one to the own database.

`ConfigureModule` writes an override without an id ahead of the first named connection of its interface, and merges a nested `config` object key by key, so the connections already registered with `dms-database` stay. It replaces a scalar or an array held where it writes an object. It refuses the step, naming the module and the key path, where that value is an object with a spread, a variable or a call, such as `config.externalConnections` written as `externalConnections: shared`, where a `config` is written as a variable, and where the object it writes into holds a member under a computed name, a method or an accessor, since that member may be the key and a second one beside it would win: write it as a plain object, then try again. A shorthand member of the key it writes, such as `config: { url }`, is replaced by an assignment for a scalar or an array, and refused for an object, whose variable it cannot read.

#### Repair a connection made before

A project connected before these steps has the catalog connection and nothing `dms-database` reads. `POST /database/connections/repair` adds what is missing for every catalog connection declared on this module's own entry. It writes the `dms-database` overrides and the `databasePins` of step 5, and never `access`, so a value set in the `dms-database` console is kept. Send `{ "dryRun": true }` to read the changes without writing them. It refuses, as `GET /database/project` does, when `dms-database`, or a module that needs a pin, is written as a version string or with a spread, unless that module pins `interface-database` after its last spread, instead of answering that nothing is missing.

The answer is an `OpResult` like `ConfigureProject`. A configuration that already holds everything answers `{ ok: true, data: { files: [] }, changes: [] }` and is not written, so a second call changes nothing.

#### Check a connection before writing it

`POST /database/connections/check` tests a database before anything is written to `antelope.config.ts` or `.env`. The driver module is not configured at that point, so the builder opens the database itself with the engine's client library: `pg`, `mongodb` or `rethinkdb-ts`. They are optional peer dependencies of this module, required only when their engine is checked, first from this module and then from the project. When the client is installed in neither, the answer is `reachable: false` with a `reason` such as `Install pg to connect a PostgreSQL database.`

The answer reads as follows:

- `reachable` is `true` when a server answered, even to refuse the sign-in. `latencyMs` is the round trip of the first query of the signed-in account, and `user` is the account the server reports.
- `canWrite` is `true` when the account may insert, update or delete in any relation it can see, as the catalog of the engine's driver decides. `canRead` is `true` when it may read any of them, or when it sees none. A MongoDB server without access control gives full privileges, whatever the database holds: an empty database, or one of views, reads and writes there.
- `reason` is a short sentence for the person who connects, present when the database is unreachable, refuses the sign-in or cannot be read. It never holds the URL, the password or a query a driver echoes in its message.

A RethinkDB URL with no database after the port is answered once the account has signed in, with `reachable: true`, `user`, no access and a `reason` saying the URL names no database.

The check ends within three times the connect timeout of five seconds, and closes every connection it opened, when the database answers and when the deadline passes first. It never waits for a server to close its end before it answers, and it shuts a socket that is still open a quarter of a second after it said goodbye, so a server that ignores the goodbye changes neither the answer nor what stays open. For RethinkDB it deletes a key no row has to learn whether the account may write, so it changes no row.

### Edit a whole page

A client that changes a whole page holds a draft and writes it once, rather than replaying each edit. It uses three routes in this order:

1. `GET /api/builder/page?ref=/dashboard` returns the `PageStructure`, with its `version`.
2. `POST /api/builder/page/preview` returns the serialized layout of the draft. The client calls it as often as it needs.
3. `POST /api/builder/page/blocks` with `expectedVersion` writes the draft in one transaction and one typecheck. If the page changed since the read, it fails with `stale` instead of overwriting it.

Every write also fails with `stale`, with or without `expectedVersion`, when a file it edits changes on disk while the write runs. Nothing is written. Read the page again and retry.

## Make your blocks editable

The builder reads blocks back by their shape. A hand-written declaration that matches the grammar of a DMS factory call is as editable as a generated one. A declaration that departs from that grammar shows as opaque, and the builder does not rewrite it.

A factory imported from its documented subpath (`@antelopejs/interface-dms/base/kpi-card`) reads exactly like one imported from the `base` barrel. A component the catalog has no factory for, such as one a helper of your own returns, shows as an opaque block, and the builder keeps it as written when it saves the page.

A block type declared with `RegisterBlockType` appears in the catalog. The catalog takes its label, icon and description from the definition's `meta`, and describes its options from its `schema`. A block's `.meta({ name, description, icon })` names the permission the DMS registers for it, which is how the role editor shows it.

## Languages

The builder's texts ship in `frontend-vue/i18n/locales/builder-en-GB.json` and `builder-fr-FR.json`, under the `dms_builder` namespace. They cover the database connect flow. The DMS frontend loader merges them into the app's catalog like the texts of any module. English is the fallback locale, so a language the module does not ship reads in English. An app can override any text by declaring the same key in its own locale files.
