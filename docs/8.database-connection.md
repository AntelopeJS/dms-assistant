**Start from an existing database** in the assistant's onboarding popup connects a database you already run. The popup calls the module's routes under `/api/builder/database`. They wire the database into `antelope.config.ts`, analyse its tables and map them into pages, through the external-database operations of `@antelopejs/dms`. [External databases](/docs/interfaces/builder/external-databases) in the builder interface docs describes those operations. This page lists the routes, the keys that control them and what they write.

Every route requires an authenticated tenant owner. The routes need a module that implements `@antelopejs/interface-api`, such as `@antelopejs/api`.

## Configuration

The keys live under `builder` in the `config` block of the module's entry in `antelope.config.ts`, which `ajs project modules add @antelopejs/dms-assistant` writes. `@antelopejs/dms-builder` read them at the top level of its own entry.

| Option | Type | Default | Description |
| --- | --- | --- | --- |
| `builder.projectRoot` | `string` | the process working directory | The app's source root. A relative path resolves against the process working directory. Every module, table and page that connecting a database writes lands under it. |
| `builder.api.enabled` | `boolean` | the project's development mode | Mounts the `/api/builder/database` routes, or keeps them off. |

Set `builder.projectRoot` when the backend's working directory is not the app's source root:

```ts fragment [antelope.config.ts]
"dms-assistant": {
  source: { /* … */ },
  config: {
    builder: {
      projectRoot: __dirname,
    },
  },
},
```

The builder that the DMS MCP server drives reads its own options under the `builder` key of the `dms` module. [Configuration](/docs/building/configuration) in the DMS docs lists them.

::note
The module does not read a `factoring` option. Remove it if an older configuration still holds one.
::

## When the routes are on

The routes rewrite source files. When `builder.api.enabled` is unset, they follow the core's development flag (`GetRuntimeInfo().dev`). The DMS reads the same flag for dev reload. The module does not read `NODE_ENV`.

| Command | Routes |
| --- | --- |
| `ajs project dev`, `ajs project dev -w` | On |
| `ajs project start`, which starts the project from its build | Off. The process mounts no `/api/builder/database` routes, so they answer `404`. |

`builder.api.enabled: true` mounts the routes on a started build. `builder.api.enabled: false` keeps them off in development. When the routes are off, the module never imports their controller.

::warning
With `builder.api.enabled: true` on a deployment, tenant owners can rewrite the deployed sources. Do not turn the routes on in a deployment only to make them answer.
::

`GET /api/builder/database/connections` answers the catalog connections of the project, `[]` before you connect one. A `404` means the routes are off in this process.

## Routes

Every path below sits under `/api/builder`. Of these routes, only `POST /database/sample` answers rows of the external database.

| Method | Path | Body or query | Answer |
| --- | --- | --- | --- |
| `GET` | `/database/connections` | | Each catalog connection, with `id` and what its provider reports (`engine`, `version`, `database`, `role`) or an `error` |
| `POST` | `/database/connections/repair` | `{ dryRun? }` | An `OpResult` of the configuration change, or an empty success when nothing is missing. See [Repair a connection made before](#repair-a-connection-made-before). |
| `POST` | `/database/connections/check` | `{ engine, url }` | `{ reachable, latencyMs?, user?, canRead, canWrite, reason? }`. Owner only, and `403` outside development. `400` for an `engine` other than `postgres`, `mongodb` or `rethinkdb`, or a `url` that is not of that engine. See [Check a connection before writing it](#check-a-connection-before-writing-it). |
| `POST` | `/database/analyse` | `AnalyseDatabaseInput` | `AnalyseDatabase` |
| `GET` | `/database/analysis` | `?id=` or `?connection=` | `GetAnalysis`, or the latest analysis of the connection. `404` when the connection has none. |
| `POST` | `/database/map` | `MapResourcesInput` | `MapResources` |
| `GET` | `/database/mapping` | `?connection=&module=` | `GetMapping` |
| `GET` | `/database/project` | | `{ modules, self, ownDatabase?, databasePins, dmsDatabase? }`. See [What connecting a database writes](#what-connecting-a-database-writes). |
| `POST` | `/database/project` | `{ steps, opts?, variables? }` | `ConfigureProject`. With `variables`, the route first writes their development values into `.env`. |
| `GET` | `/database/connection` | `?connection=` | `{ wiring, details }`. `404` for an unknown connection. |
| `POST` | `/database/connection/remove` | `{ connection, dryRun? }` | An `OpResult` of the configuration change |
| `POST` | `/database/connection/url` | `{ connection, url }` | An `OpResult` with the `variable` it set. A URL without a password keeps the current one. |
| `POST` | `/database/sample` | `{ connection, relation, columns, limit }` | The sampled rows. `404` for an unknown connection. |

A route that refuses the request answers `422` with `{ code: "refused", message }`.

`POST /database/map` writes only code that compiles across the whole project. When it answers `typecheck_failed`, nothing is written, and the error lists each diagnostic with its file and line. A type error elsewhere in the project blocks the write too.

## What connecting a database writes

The **Connect a database** form plans one `ConfigureProject` batch from the answer of `GET /database/project`, and sends it to `POST /database/project`. The answer holds these fields:

- `self` is the id `antelope.config.ts` gives this module.
- `ownDatabase` is the project's default `interface-database` provider.
- `databasePins` lists the modules to pin to it.
- `dmsDatabase` is the id of the `dms-database` entry.

`ownDatabase` and `dmsDatabase` are absent when the project has no such database or module.

`GET /database/project` refuses with `422` in these cases:

- The configuration does not say plainly which database is the default.
- A module that imports `interface-database` and does not provide it is not written as an object literal. A version string, an entry with a spread and an entry with a member under a computed name all count, because the route cannot write their pin.
- `dms-database` is written that way under its id or its package name.
- A module is keyed by a computed name, a method or an accessor. It may be `dms-database` or a module that needs a pin.

An entry with a spread that already pins `interface-database` in an `importOverrides` written after its last spread or computed name counts as pinned, since a later key wins.

The batch writes these steps in order:

1. `AddModule` for the engine's driver, with its URL read from a variable.
2. `CreateLocalModule` for the module that holds the tables, pinned to the driver.
3. `ConfigureModule` on `self`, declaring the catalog connection under the connection's id.
4. `ConfigureModule` on `dms-database`, when the project has it and an own database. The entry then reads, for a connection `erp` served by the driver `builder-db-erp` over a project whose own database is `mongodb`:

   ```ts
   const modules = {
     "dms-database": {
       importOverrides: [
         { interface: "@antelopejs/interface-database", source: "mongodb" },
         { interface: "@antelopejs/interface-database", source: "builder-db-erp", id: "erp" },
         { interface: "@antelopejs/interface-database-catalog", source: "builder-db-erp", id: "erp" },
       ],
       config: { externalConnections: { erp: { access: "read" } } },
     },
   };
   ```

   The first entry of `interface-database` without an id is the binding a plain import reaches, so the own database comes first. The connection keeps one id on both interfaces and in `externalConnections`. `access` is `read`, or `read-write` when the form chose it, and `read` when absent.
5. One `ConfigureModule` for each module in `databasePins`. Once a second `interface-database` provider exists, core refuses to start a module that imports `interface-database` without a pin. Each configured module that imports it, does not provide it and has no pin without an id therefore gets one to the own database.

Every file lands under `builder.projectRoot`, in the project's own sources:

- the driver module and the module that holds the tables, in `antelope.config.ts`,
- the connection's URL variable, in `.env`,
- the mapped tables as `Table`, `DataController` and model files, and their pages as `PageController` classes.

Commit these files like any other code, except `.env`.

### Repair a connection made before

A project connected before these steps has the catalog connection and nothing `dms-database` reads. `POST /database/connections/repair` adds what is missing for every catalog connection declared on this module's own entry. It writes the `dms-database` overrides and the `databasePins` of step 5, and never `access`, so a value set in the `dms-database` console stays. Send `{ "dryRun": true }` to read the changes without writing them. It refuses as `GET /database/project` does, instead of answering that nothing is missing, when `dms-database` or a module that needs a pin is written as a version string or with a spread. A module that pins `interface-database` after its last spread is not refused.

The answer is an `OpResult` like `ConfigureProject`. A configuration that already holds everything answers `{ ok: true, data: { files: [] }, changes: [] }` and is not written, so a second call changes nothing.

### Check a connection before writing it

`POST /database/connections/check` tests a database before anything is written to `antelope.config.ts` or `.env`. The driver module is not configured at that point, so the route opens the database itself with the engine's client library: `pg`, `mongodb` or `rethinkdb-ts`. They are optional peer dependencies of this module, required only when their engine is checked, first from this module and then from the project. When the client is installed in neither, the answer is `reachable: false` with a `reason` such as `Install pg to connect a PostgreSQL database.`

The answer reads as follows:

- `reachable` is `true` when a server answered, even to refuse the sign-in. `latencyMs` is the round trip of the first query of the signed-in account, and `user` is the account the server reports.
- `canWrite` is `true` when the account may insert, update or delete in any relation it can see, as the catalog of the engine's driver decides. `canRead` is `true` when it may read any of them, or when it sees none. A MongoDB server without access control gives full privileges, whatever the database holds. An empty database, or one of views, reads and writes there.
- `reason` is a short sentence for the person who connects, present when the database is unreachable, refuses the sign-in or cannot be read. It never holds the URL, the password or a query a driver echoes in its message.

A RethinkDB URL with no database after the port is answered once the account has signed in, with `reachable: true`, `user`, no access and a `reason` saying the URL names no database.

The check ends within three times the connect timeout of five seconds. It closes every connection it opened, both when the database answers and when the deadline passes first. It never waits for a server to close its end before it answers. It shuts a socket that is still open a quarter of a second after it said goodbye, so a server that ignores the goodbye changes neither the answer nor what stays open. For RethinkDB, it deletes a key no row has to learn whether the account may write, so it changes no row.

## Languages

The texts of the database connect flow ship in `frontend-vue/i18n/locales/builder-en-GB.json` and `builder-fr-FR.json`, under the `dms_builder` namespace. The DMS frontend loader merges them into the app's catalog like the texts of any module. English is the fallback locale, so a language the module does not ship reads in English. An app can override any text by declaring the same key in its own locale files.
