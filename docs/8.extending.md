## Ship skills with your module

The assistant loads the skills that `antelopeJs.skills` declares in every loaded module, in the dependencies of those modules, and in the project's own dependencies, devDependencies included.

### The skill file

Each skill is a folder under a declared skills directory, with a `SKILL.md` inside:

```md [skills/my-module/SKILL.md]
---
name: my-module
description: Explains when and how to use my-module. Use when the user mentions invoices, billing pages, or the InvoiceService.
icon: i-lucide-receipt
category: billing
tags: [invoices, billing, pages]
---

# my-module

When to use it, its key APIs and pages, and its gotchas. Link to the docs for the rest.
```

The catalog reads five frontmatter fields:

| Field | Required | Value |
| --- | --- | --- |
| `name` | Yes | The skill's name. The agent sees it as `<module>:<name>`. |
| `description` | Yes | What makes the agent pick the skill. Name the cases that should trigger it. |
| `icon` | No | The icon of the skill's card. |
| `category` | No | The category of the skill's card. |
| `tags` | No | An inline list, such as `[invoices, billing]`. |

The catalog skips a `SKILL.md` that has no frontmatter, no `name` or no `description`.

Under Claude Code, three skill features that act before the owner is asked are switched off, since each could hand the agent the project's `.env` values:

- Inline shell commands, `!` followed by a command in backticks, do not run: the agent reads `[shell command execution disabled by policy]` in their place.
- `hooks` in the frontmatter do not run.
- An `@` reference to `.env` or a `.env.*` file, or to a link to one, is refused. The templates `.env.example`, `.env.sample` and `.env.template` stay readable.

Write what the skill needs into the file, or have the agent run a command as a tool call, which asks the owner first.

### The declaration

`antelopeJs.skills` in `package.json` lists the skills directories, relative to the package. The package must also publish them in `files`:

```json [package.json]
{
  "files": ["dist", "skills"],
  "antelopeJs": {
    "skills": ["./skills"]
  }
}
```

### When the skills load

The module collects the declared directories when the backend starts and passes them to the sidecar. A new or changed skill appears after a backend restart, in the agent.

Before the modules' directories, the assistant loads the DMS workflow skills of `@antelopejs/agent-skills`, such as `dms-pages`, `dms-builder-mcp` and `dms-mockup`, under the plugin name `antelopejs`. When two directories ship a skill with the same name, the agent loads the first one only. A module's own copy of a workflow skill therefore loses to the workflow skill.

::tip
The same declaration lets the `antelopejs` plugin from [AntelopeJS/agent-skills](https://github.com/AntelopeJS/agent-skills) sync your skills into a project's `.claude/skills/` for Claude Code, or `.agents/skills/` for Codex, outside the dashboard.
::

## The chat uses the builder tools of the DMS

The chat reaches the [builder](/docs/interfaces/builder/introduction) through the `dms` MCP server of `@antelopejs/dms`, as `mcp__dms__builder_catalog`, `mcp__dms__builder_add_block`, `mcp__dms__builder_create_page` and the other `builder_*` tools. [Where the chat's tools come from](/docs/modules/assistant/configuration#where-the-chats-tools-come-from) lists both servers. New chats start in Safe mode, unless the **Safe mode** setting is off, which makes Code mode the default.

The agent picks one skill for each generation mode:

| Skill | Shipped by | When the agent uses it |
| --- | --- | --- |
| `dms-builder-mcp` | `@antelopejs/agent-skills` | Safe mode. The agent changes pages only through the `builder_*` tools. |
| `dms-assistant-code-mode` | This package | Code mode. The agent edits a page's code while the user watches the page. |

The workflow skills of `@antelopejs/agent-skills` also cover pages over an existing database (`dms-external-database`), pages that show data (`dms-page-design`) and mockups (`dms-mockup`, `dms-mockup-build`). This package ships `dms-assistant` beside `dms-assistant-code-mode`, for the module's own setup.

## Owner-only routes

Every route below requires an owner. A route that relays to the sidecar answers `503 { message }` while the sidecar is down. The usage routes answer empty figures instead, and the banner routes answer 204.

| Route | Purpose |
| --- | --- |
| `GET /ai/status`, `POST /ai/sidecar/restart` | The live status of the signed-in owner's own conversations (`offline` when the sidecar does not answer), and a restart |
| `GET /ai/status/banner` | The banner of the Settings page: offline, a failed turn or requests waiting (204 when all is well) |
| `GET /ai/sidecar-info` | Whether the sidecar runs, has given up or is disabled. Each call starts the sidecar again if it stopped. |
| `GET /ai/metrics/usage`, `usage/summary` | The token figures of Settings |
| `GET /ai/activity`, `/ai/activity/:id`, `/ai/activity/export.csv` | The audit log, one call, and the CSV export. `from` and `to` set the period. |
| `GET /ai/changes`, `/ai/changes/:id`, `/ai/changes/:id/undo-preview`, `/ai/changes/:id/undo-confirm` | Change sets, a diff, what Undo restores (the chat's preview lists only the later sets of conversations the signed-in user may use), and the Undo dialog |
| `POST /ai/changes/:id/undo`, `/ai/changes/:id/redo` | Undo (`{ includeLater? }`) and Redo |
| `GET /ai/settings`, `PUT /ai/settings` | The settings form and the Guard rails card. `PUT` takes the one field an instant save sends. The Safe mode switch is the field `safeMode`, stored as `generationMode` (`safe` or `vibe`). A guard rail (a default mode, Safe mode, an ask, local skills) is written only with the header `x-dms-ui-assistant: 1`, the others without it. |
| `GET /ai/onboarding`, `POST /ai/onboarding/claude-token`, `POST /ai/onboarding/provider` | The onboarding window: where each login stands, a pasted Claude token (checked with Anthropic, then saved, and only with the header `x-dms-ui-assistant: 1`), and the provider the assistant runs on. No answer carries a token. |
| `GET /ai/codex/account/banner`, `POST /ai/codex/callback`, `POST /ai/codex/logout` | The ChatGPT account banner of Settings, the pasted return address of a remote sign-in, and the sign-out |
| `GET /ai/channel/events`, `POST /ai/channel/:connectionId/messages` | The chat's event stream and the client's messages |

The sidecar calls `/ai/logs` and `/ai/pages-registry` with its own token in the `x-dms-assistant-token` header. They refuse any other caller. `GET /ai/health` needs no sign-in.

## Roles

The Assistant pages are built from DMS blocks, with a custom component only where no block draws the screen. Every page, block and child carries `$dms_assistant.*` metadata, so the role editor lists them with translated names.

## Frontend

The chat panel, `DmsAssistantChatPanel`, is registered as a docked side panel of the dashboard with `registerSidePanel`, and renders once for the whole app. The command palette's assistant mode answers with `DmsAssistantPaletteAnswer`, registered with `registerCommandPaletteAssistant`.

### Start a conversation from your module

Another module's layer can open the assistant on a new conversation without depending on `dms-assistant`. The plugin provides its actions under a global key. Inject them with a `null` default:

```ts
import { inject } from "vue";

interface AssistantActions {
  readonly isAvailable: boolean;
  startConversation(prompt: string, options?: { mode?: "plan" | "normal"; send?: boolean }): void;
}

const assistant = inject<AssistantActions | null>(Symbol.for("dms-assistant:assistant-actions"), null);
```

- `null` means that `dms-assistant` is not installed, or that the project does not run in development. Offer nothing.
- `isAvailable` is reactive. It is `false` until the assistant runs in this tab, and stays `false` for a guest or with the sidecar disabled. Show a button only while it is `true`.
- `startConversation(prompt)` opens the panel on a new conversation with `prompt` in the composer. It sends nothing: the person reads the prompt and presses **Send**.
- `{ send: true }` sends `prompt` as the first message once the stream is up, and leaves the composer empty.
- `{ mode: "plan" }` sets the conversation to plan mode first. The agent then ends its turn with a plan, which the person approves with **Run with Ask first**.

The types are `PublicAssistantActions` in `frontend-vue/app/runtime/assistant-actions.ts`.

### Open the onboarding window from your module

The onboarding window is available the same way, under `Symbol.for("dms-assistant:onboarding")`:

```ts
import { inject } from "vue";

interface Onboarding {
  readonly isAvailable: boolean;
  open(step?: "connect-database"): void;
}

const onboarding = inject<Onboarding | null>(Symbol.for("dms-assistant:onboarding"), null);
```

- `null` means that `dms-assistant` is not installed, or that the project does not run in development. `dms-database` hides its **Connect a database** entry then.
- `isAvailable` is reactive, and `true` once the assistant runs in this tab and its onboarding answered.
- `open()` opens the window as its widget would. `open("connect-database")` opens it on the **Connect your database** form, after the AI step when no login works yet. Without the builder, the form does not exist, and the window opens as `open()` does.

A link to any dashboard page with `?assistant=connect` does the same as `open("connect-database")`, then takes the parameter out of the address. The types are `PublicOnboarding` in `frontend-vue/app/onboarding/public.ts`.

## Requests from the mockup viewer

The mockup viewer of the DMS hands requests to the assistant through the cancelable `dms:assistant-prompt` window event. The assistant claims the event, so the viewer does not fall back to showing the prompt to copy, and opens its panel. The `source` of the event decides what happens next:

| `source` | Detail | What the assistant does |
| --- | --- | --- |
| `connect-data` (sent by DMS 0.20.x), `custom-zone` | `prompt`, and the `block` it is about | Puts the prompt in the composer, with the block as context. Nothing is sent until you send it. |
| `new-mockup` | `prompt`, the start of a sentence such as "Draft a mockup of " | Starts a new conversation with the prompt in the composer, focused with the caret at its end. Nothing is sent until you send it. |
| `build` | `prompt`, the mockup name. `title`, its display title. `target.pageRef`, an existing page to build into. | Starts a new conversation and sends the build request at once. The reply ends with a link to each page built. |
| `resolve-comments` | `prompt`, the mockup name. `title`, its display title. `page`, the one page of the spec to limit the run to. | Starts a new conversation and sends the request at once. The assistant lists the open comments, patches the spec from each comment's block, resolves the comment, then reports what changed and what stays open with its question. A comment pinned to a page counts as a comment on the whole page. |

When `title` differs from the name, the request names the mockup as "Shop admin" (shop-admin), else by its name alone. DMS 0.20.x sends no `title`. A detail that matches none of these rows is left to the viewer.

The `resolve-comments` request carries its steps, so the run loads no skill. In Safe mode, it needs only the `mockup_annotations`, `mockup_patch_spec` and `mockup_resolve_annotation` tools, which Safe mode allows.

A second `build` or `resolve-comments` for the same mockup, sent while the first one runs, starts nothing. The assistant still claims the event and opens the panel on the running conversation. Once that run has finished, failed or been stopped, the next request starts a new conversation.

### Run state

The assistant tells the window when such a run starts and ends, so the viewer can show it:

| Window event | Sent by | Detail |
| --- | --- | --- |
| `dms:assistant-run` | The assistant | `{ mockup, source, running }`. `mockup` is the mockup name, `source` is `build` or `resolve-comments`, and `running` is `true` when the run starts and `false` when it finishes, fails or is stopped. |
| `dms:assistant-run-query` | The viewer | None. The assistant answers with a `dms:assistant-run` of `running: true` for each run going on. |

The viewer sends `dms:assistant-run-query` when it mounts, so a page reload during a run shows the right state. The assistant keeps the runs in the tab's `sessionStorage`, and drops the ones its next conversation list shows as over. The types are `MockupAssistantRun` and `MockupRunSource` in `frontend-vue/app/runtime/assistant-prompt.ts`, next to the prompt's.
