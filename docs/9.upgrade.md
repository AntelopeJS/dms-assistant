---
title: Upgrade from the earlier modules
description: How the module moves the builder settings and catalog connections of the earlier builder and assistant modules onto the entry of the DMS, and when an old entry is safe to remove.
mode: reference
---

Before `@antelopejs/dms` served the builder, this module, `@antelopejs/dms-builder` and `@antelopejs/dms-ai` read the builder's settings and catalog connections on their own entries. In development, once every module has started, this module moves them to the entry of `@antelopejs/dms`. That entry is the `self` that `GetDatabaseProject` answers. The move is one `ConfigureProject` batch.

| Moved from | Setting | Moved to, on the `@antelopejs/dms` entry |
| --- | --- | --- |
| this module's entry | `builder.projectRoot` | `builder.projectRoot` |
| a `@antelopejs/dms-builder` entry | `projectRoot` | `builder.projectRoot` |
| a `@antelopejs/dms-builder` entry | `api.enabled` | `builder.enabled` |
| a `@antelopejs/dms-ai` entry | `backendUrl` | `mcp.backendUrl`, the origin the bridge of the DMS MCP server calls |
| any of these entries, or a `@antelopejs/dms-ai` entry | each `importOverrides` element with an `id` for `@antelopejs/interface-database` or `@antelopejs/interface-database-catalog` | the same element |

The connect flow of `@antelopejs/dms-builder` declared each catalog connection on the `dms-ai` entry too, so the move reads that entry after the other two.

The move reads every entry at the top level of `modules` in `antelope.config.ts`, whether it loads, is `disabled: true` or failed to load. It finds an old entry by its package. For an entry that loaded, that is the `name` in the `package.json` the core loaded it from, whatever its source. Otherwise the source names it: the `package` of a package source, the `name` in the `package.json` of a `local` or `local-folder` path, or a `git` remote whose repository is `dms-builder` or `dms-ai`. When the source cannot tell, an entry keyed `dms-builder` or `dms-ai` counts as that package. The settings come from `ListModuleDeclarations` of `@antelopejs/interface-core`, which evaluates the file as a start does. The connections come from `ListEntryConnections` of `@antelopejs/interface-dms-builder`, which reads them as the file writes them. With a key written twice, both read the last entry. Neither sees an entry that `ajs project modules remove` deleted, so the order in [Install](https://github.com/AntelopeJS/dms-assistant#install) removes the old entries last.

Neither reads `environments.<env>.modules`. The module parses `antelope.config.ts` with the project's own TypeScript, an optional peer dependency. It reads the configuration where `@antelopejs/dms` does: the default export, or the first argument of its call. It names a `dms-builder` or `dms-ai` entry only for the `importOverrides` it read for that entry in an environment. An environment that only disables an old entry, or names a version, gives it no binding. When it cannot be sure, it warns that it could not read `environments`, says why, and names every `dms-builder` and `dms-ai` entry. That happens when the project has no TypeScript, or when the configuration, its `environments` or an entry there is not written in the file as plain object literals, as with a spread, a variable or a base imported from another file. Move each catalog connection an environment gives an old entry to the `@antelopejs/dms` entry of that environment by hand. This module's own entry stays, so the check leaves it out.

This module keeps its own `builder.api.enabled`, which mounts the routes. `@antelopejs/dms` resolves a relative `builder.projectRoot` against the process working directory, the folder `ajs` runs from, as the old entries did. So the move keeps the folder the builder edits:

- When `ajs` runs from the folder of `antelope.config.ts`, the move writes a `projectRoot` relative to that folder, with `/` separators, so the committed file holds a value that works on every machine. A `projectRoot` that resolves to that folder, such as `projectRoot: __dirname`, moves nothing, since `@antelopejs/dms` reads that folder when `builder.projectRoot` is unset.
- When `ajs` runs from another folder, such as with `ajs project dev -p ./my-app`, the move writes no `projectRoot`. A relative value would name another folder once `ajs` runs from the project folder. The module logs one warning with the absolute folder the old entry names. Set `builder.projectRoot` on the `@antelopejs/dms` entry to it by hand.

The move follows these rules:

- A connection moves with every interface its id is declared for. When the `@antelopejs/dms` entry declares the same id the same way, the copy on the old entry is removed.
- When the `@antelopejs/dms` entry holds a connection id or a setting differently, it keeps its own and the old entry keeps its own. The module logs a warning that names both, at every start, until you remove one of them. Two `projectRoot` values that resolve to the same folder hold it the same way.
- A `builder` or `mcp` key that the `@antelopejs/dms` entry declares stays its own, whatever it evaluates to. With `builder: { projectRoot: process.env.DMS_ROOT }` and `DMS_ROOT` unset, the key holds `undefined`. The move keeps the expression and warns with both values.
- The batch never writes `config.externalConnections` on `dms-database`, so each connection keeps the access that `dms-database` grants it. It removes a connection from every entry, then writes it back on the entries that keep it, `dms-database` included.
- When `ListEntryConnections` cannot read an entry's bindings (`invalid_config`), no connection moves, since removing a connection takes it off that entry too. It cannot read an `importOverrides` held in a variable or a spread, nor an entry that a spread or a computed name written after it in `modules` may override. The connections go into the module's one warning of what to move by hand. The settings still move.
- An entry that `ListEntryConnections` does not find written (`not_found`) holds back no other connection. Nor does any entry when `@antelopejs/dms` finds no `antelope.config.ts` (`unsupported`), as when `ajs` runs from another folder, since `ConfigureProject` writes nothing there either. For a `dms-builder` or `dms-ai` entry, either answer means the move could not read its connections, so the module names them in its warning of what to move by hand. With `unsupported`, it also says to start `ajs` from the project folder. This module's own entry stays, so it is not named.
- The module logs what moved, only when something moved.

`ConfigureProject` writes nothing when it refuses the batch, and nothing moves when `GetDatabaseProject` refuses. Each start logs at most one warning of what was not moved, besides the `projectRoot` warning above when `ajs` runs from another folder. It names each refusal once, those of `ListEntryConnections` included, and every setting and connection to move by hand. `@antelopejs/dms` looks for `antelope.config.ts` under its own `builder.projectRoot`, or under the process working directory when that key is unset. So a project started from another folder gets a refusal while the `@antelopejs/dms` entry has no `builder.projectRoot`. Set that key there by hand.

After the move, the module logs one line for each `dms-builder` and `dms-ai` entry, by the name `antelope.config.ts` gives it:

- `dms-builder: nothing left to move, safe to remove` when the move read the entry's connections and `environments`, and the `@antelopejs/dms` entry holds every connection and setting the entry held. No other line says an entry is safe to remove.
- `dms-builder: 1 connection(s) still here, move them before removing` when a connection, a setting, or the `importOverrides` an environment gives the entry stays on it. The line names each setting and environment.
- `dms-builder: not safe to remove, the move could not read its connections`, or `environments of antelope.config.ts`, when the move could not read them.

`@antelopejs/dms` loads `antelope.config.ts` before the move writes it, so the process that moves serves none of the moved connections. Until the next start, `GET /api/builder/database/connections` answers `[]` and the onboarding shows its plain Connect form. On the start that moved, the notice of what moved and each line end with `Start the project again for @antelopejs/dms to serve what moved.`

A second start writes nothing. It logs only what still needs a person: standing conflicts, can't-read warnings and the per-entry lines.
